# План изменений VaraGov по обратной связи от 3 ноября

Дата: 05.11.2026. Основание: переписка и два скриншота пользователя,
HANDOFF.md, SPEC.md и текущее состояние репозитория (`4dab3da`).
Это план реализации; продуктовый код в рамках исследования не менялся.

Уточнение пользователя: счётчик должен учитывать **только комментарии
VaraGov**.

## 1. Понятный ответ: проходит ли референдум

### Что обнаружено

- В `components/HistoryPanel.tsx` уже реализованы текущие значения, пороги,
  маркеры и надпись `Passing` / `Failing`. В
  `app/referenda/[id]/page.tsx` сравниваются оба показателя с текущими кривыми.
  Задача частично реализована, но формулировки не отвечают на вопрос из переписки.
- На первом скриншоте approval = 100% при требуемых 52,2%; support = 0,10%
  при требуемых 0,75%. **Approval выполнен, support — нет: по текущим
  порогам референдум ещё не проходит.**
  При этом support-порог может впоследствии опуститься до текущего support:
  это объясняет возможность будущего прохождения, но не означает прохождение
  в момент снимка.
- Сейчас `passingNow` становится `false`, когда ещё не загружены issuance или
  параметры трека. Из-за этого неполные данные могут выглядеть как `Failing`.
  Для Preparing/Queueing также выводится оценка по начальным порогам без
  объяснения, что решение ещё не началось.
- Support 0,10% и порог 0,75% занимают почти невидимую часть шкалы 0–100%.
- Сам скриншот не доказывает ошибку арифметики. Существующий
  `scripts/check-curves.ts` проходит, но проверяет лишь базовые свойства формул.

### Изменения

1. Перед реализацией воспроизвести проблемное состояние и сравнить версию
   развёрнутого приложения с репозиторием. Проверить значения на одном
   finalized-блоке: tally, active issuance, трек, начало Deciding и текущие
   пороги. По снимку нельзя восстановить точный прогноз без трека и блока.
2. Вынести оценку в общую функцию, например `lib/chain/referendum-outlook.ts`:
   текущие показатели, пороги, причины невыполнения, состояние загрузки и
   условный прогноз. Сравнения выполнять с точностью runtime/Perbill,
   округлять только выводимые числа.
3. Вместо одного двусмысленного `Failing` показать различимые состояния
   (интерфейс остаётся англоязычным):
   - `Decision not started` — Preparing/Queueing;
   - `Below current thresholds` — указать конкретно approval и/или support;
   - `Current thresholds met` — оба порога выполнены;
   - `Confirming` — состояние из цепи с оставшимся временем;
   - `Loading voting requirements` / ошибка чтения — если данных недостаточно;
   - окончательный результат — по terminal state цепи.
4. Для каждой метрики явно показать «сейчас / требуется». Добавить доступное
   пояснение: approval учитывает conviction; support берётся из `tally.support`
   без множителя conviction и делится на active issuance. Support не следует
   называть всеми токенами, участвовавшими в голосовании.
5. Добавить условный прогноз: когда **оба** порога будут выполнены при
   неизменных tally и issuance, затем ожидаемый момент одобрения с учётом
   confirmPeriod. Для уже Confirming брать срок из `confirmingUntil`.
   Если пороги недостижимы при текущих голосах, сказать, что нужны новые
   голоса. Правила на границе decisionPeriod сверить с runtime.
6. Визуально увеличить шкалу support до явно подписанного диапазона,
   включающего текущее значение и порог. Сохранить `.panel`, семантические
   цвета и остальные элементы Chamber & Gazette. Продублировать краткую
   оценку в списке активных token-holder референдумов.
7. Обновлять оценку по согласованному finalized-состоянию; не смешивать
   порог нового блока с tally из более старого запроса. Данные для ongoing
   по-прежнему получать из RPC.

**Файлы:** `lib/chain/curves.ts`, `lib/chain/hooks.ts`, новая функция оценки,
`app/referenda/[id]/page.tsx`, `components/HistoryPanel.tsx`,
`components/ReferendaDirectory.tsx`, `components/referenda.tsx`;
при необходимости `components/CurveChart.tsx`.

**Приёмка:** сценарий со скриншота сообщает, что текущий support ниже порога,
и отдельно показывает условный прогноз, если его можно вычислить. Нет
ложного `Failing` во время загрузки. Видны причина, оба порога и срок
Confirming. Проверены границы порогов, нулевые голоса, подготовка, отсутствие
RPC, переход в Confirming и его прерывание. Мобильная и настольная версии,
светлая и тёмная темы показывают одинаковый смысл.

Примечание: в Fellowship другая база support (`bareAyes` и состав допустимых
участников), поэтому token-holder формулу нельзя автоматически применять
к странице Fellowship. Расширение оценки на ranked collective требует
отдельной проверки его runtime-правил.

## 2. Количество комментариев на главной

### Что обнаружено

- `/` перенаправляет на `/referenda`; список использует `useRefMeta()` и
  `GET /api/content`.
- API возвращает заголовки, трек и поисковый текст, но не количество
  комментариев. У `ReferendumRow` соответствующего параметра нет.
- На странице референдума число уже есть: `comments.length`, включая ответы.

### Изменения

1. Добавить в существующий список метаданных `commentCount` из Prisma
   `_count.comments`. Загружать счётчики одним общим HTTP-запросом со списком,
   без отдельной загрузки комментариев для каждой строки.
2. Передать число через `RefMeta` и `ReferendaDirectory` в `ReferendumRow`.
   Показать иконку `MessageSquare` из lucide-react и число, включая 0;
   предусмотреть понятную подпись для screen reader.
3. Считать все опубликованные комментарии вместе с ответами, как в деталях.
   Редактирование не меняет счётчик. После создания комментария обновлять
   общий query cache; при открытом списке опрашивать его примерно раз в
   30 секунд и обновлять при возвращении на вкладку.
4. При недоступной БД показывать неизвестное число, а не подставлять 0.
   Живой список из RPC должен оставаться доступным.

**Файлы:** `app/api/content/route.ts`, `lib/content.ts`,
`components/ReferendaDirectory.tsx`, `components/referenda.tsx`,
`components/Comments.tsx`. Миграция БД для счётчика не требуется.

**Приёмка:** число в строке совпадает с деталями, новый комментарий/ответ
увеличивает его, редактирование сохраняет число; обновление видно после
возврата из деталей и у другого пользователя в пределах интервала опроса.
Число читается и на мобильном экране.

## 3. Заголовок и описание Fellowship, включая #75

### Что обнаружено

- Fellowship-страница выводит шаблонный заголовок. В ней нет `useContent`,
  Markdown-описания и кнопки `EditContent`. Список Fellowship также не
  получает сохранённые заголовки.
- Существующий API проверяет автора только через `api.query.referenda`,
  а редактор и anchor-функция используют только `api.tx.referenda.setMetadata`.
- `Referendum.index` — единственный первичный ключ БД, а подписанный
  `SimaPayload` не различает виды референдумов. Просто подключить нынешний
  редактор нельзя: token-holder #75 и Fellowship #75 — разные объекты.
- При проверке страницы Subsquare 05.11 Fellowship #75 отображался как
  Executed без описания. Это наблюдение по внешней странице; актуальное
  состояние и автора перед проверкой исправления нужно прочитать из RPC.
  Редактор должен поддерживать и завершённые референдумы.

### Изменения

1. Ввести явный вид референдума в контентном API, cache keys и подписанном
   payload. Отсутствие поля у старых сообщений трактовать только как
   token-holder; неверный вид или несовпадение с endpoint отклонять.
2. Для этой задачи добавить отдельную таблицу `FellowshipContent` с номером,
   автором, заголовком, Markdown, подписью, исходным payload и hash контента.
   Это позволяет сохранить существующую модель token-holder истории,
   голосов и комментариев. Подготовить добавочную Prisma-миграцию.
3. Добавить `GET/POST /api/fellowship/content` и
   `GET /api/fellowship/content/[index]`. Переиспользовать общие проверки SIMA,
   лимиты, защиту от старых версий и сериализацию конкурентных изменений.
4. Проверять автора на сервере через `fellowshipReferenda`. Если депозит и
   автор удалены из terminal state, восстановить их из архивного состояния
   перед завершающим блоком и сохранить подтверждённый результат. Подход
   уже есть в `lib/server/whitelist-links.ts`; выделить общую функцию,
   не привязывая проверку прав к поиску связанных execution-референдумов.
5. Параметризовать `EditContent`, чтение контента и anchor-функцию видом
   референдума. Для активного Fellowship использовать
   `fellowshipReferenda.setMetadata` после регистрации preimage. Подписанные
   заголовок и описание сохраняются off-chain и для завершённых референдумов;
   предложение anchor показывать только там, где оно доступно по runtime.
6. Подключить сохранённый контент к деталям, списку и поиску Fellowship,
   а также метаданным страницы и превью ссылок. Обновлять соответствующие
   cache keys после сохранения.

**Файлы:** `prisma/schema.prisma` и новая миграция, `lib/sima.ts`,
`lib/server/verify.ts`, `lib/server/advisory-lock.ts`, общий resolver автора,
новые API маршруты Fellowship, `lib/content.ts`, `components/EditContent.tsx`,
`lib/chain/metadata.ts`, `app/fellowship/page.tsx`,
`app/fellowship/referenda/[id]/page.tsx`, `lib/server/share-metadata.ts`
и вызывающие его metadata/image routes.

**Приёмка:** автор #75 может подписать и сохранить заголовок и описание;
после перезагрузки они видны в деталях и списке. Чужой кошелёк получает 403.
Содержимое и подписи двух референдумов с одинаковым номером из разных
разделов изолированы. Проверены повтор подписи, устаревшая версия,
SS58-представления одного адреса, старые token-holder payload и отказ
пользователя от необязательного anchor. Для активного Fellowship проверен
выбор правильного pallet при anchor.

## Порядок выполнения и оценка

1. Зафиксировать воспроизведение и сверить развёрнутую версию с репозиторием.
2. Первый набор изменений: оценка текущего прохождения и прогноз (задача 1).
3. Второй набор: счётчик локальных комментариев (задача 2).
4. Третий набор: схема контента, авторизация и редактор Fellowship (задача 3).
5. Общая проверка: значимые unit/API-тесты для расчётов и прав доступа,
   `npm test`, `npm run lint`, `npm run check` с dev-сервером и БД, затем
   production build после остановки dev. Ручная проверка с кошельком автора
   #75 и отдельная проверка активного Fellowship для anchor.

Предварительная оценка: **3–4 рабочих дня одного разработчика**, включая
проверки. Доступность кошелька автора и развёртывание согласуются отдельно;
сохранение самого текста #75 требует текста от автора и его подписи.

Паттерны взаимодействия Subsquare можно повторить в собственных компонентах
Chamber & Gazette. Ограничение AGENTS.md на копирование кода Subsquare
сохраняется.
